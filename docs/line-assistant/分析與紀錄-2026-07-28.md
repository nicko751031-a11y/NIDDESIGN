## 1. 摘要

「川果設計 NID DESIGN LAB」LINE 助理是一套部署於 Cloudflare(Workers + D1 + R2)的背景記錄系統:官方帳號加入公司 LINE 群組後,透過 Messaging API Webhook 保存文字訊息與附件、用 OpenAI 將文字分類為工作/聯絡/行事曆/決策/資訊,並提供管理儀表板、工作項目 API 與可訂閱的 iCalendar。機器人不在群組內回話,成功與否須由儀表板與伺服器紀錄判斷。

整體評估:**架構選型合理、文件完整度高、安全基線已建立**;主要風險集中在「單一 ADMIN_TOKEN 的權限設計」「缺少群組白名單」「Webhook 漏接後無補救機制」以及「個資保存的告知與保留政策尚未建立」。

2026-07-28 當日測試失敗已確認為 **LINE 官方平台重大故障**(Messaging API 與 Webhook 皆 Major Outage),非本系統程式錯誤。

## 2. 系統現況分析

### 2.1 架構與技術棧

| 層面 | 內容 |
|---|---|
| 入口 | `https://line.niddesignlab.com/webhook/line`(LINE Webhook + `X-Line-Signature` 驗證) |
| 執行環境 | Cloudflare Worker(`worker/index.ts`),Next.js 風格 App Router 路由結構 |
| 結構化資料 | Cloudflare D1:`messages`、`items`、`attachments` 三張表 |
| 檔案儲存 | Cloudflare R2:`groups/{GROUP_ID}/{YYYY-MM-DD}/{MESSAGE_ID}-{FILE_NAME}` |
| AI 分類 | OpenAI(預設 `gpt-5-mini`,可用 `OPENAI_MODEL` 覆寫) |
| 前端 | 靜態資源 binding(`ASSETS`)+ 圖片最佳化(`IMAGES`) |
| 網域 | 主站 WordPress 不動,LINE 助理獨立部署在子網域 `line.niddesignlab.com`,只共用 DNS |

### 2.2 資料流

1. 群組訊息 → LINE Messaging API → HTTPS Webhook(帶簽章)。
2. Worker 驗證簽章 → 查詢成員顯示名稱 → 原始事件寫入 D1 `messages`。
3. 文字訊息 → OpenAI 分類 → 產出 `items`(task / contact / calendar / decision / info,含負責人、到期時間、優先級、狀態、信心值)。
4. 附件(image / video / audio / file)→ 以 Channel Access Token 向 LINE 下載 → 寫入 R2 → 索引寫入 `attachments`。
5. 管理端:儀表板與 `/api/*`(Bearer ADMIN_TOKEN)、`/calendar.ics?token=ADMIN_TOKEN`。

### 2.3 明確的範圍界線(設計上的取捨)

- 只處理 `source.type = group`;一對一與舊式 `room` 聊天室不寫入。
- 貼圖、位置、Flex Message 只留基本紀錄,不屬檔案備份範圍。
- 機器人不回覆訊息(背景記錄模式),Auto-reply 與 Greeting 已停用。
- 一個群組同時只能有一個 Messaging API Bot,群組必須邀請 `@549mpmon`。

## 3. 強項

1. **職責分離清楚**:WordPress 主站與 LINE 助理完全獨立,互不影響部署與故障範圍。
2. **原始資料保真**:`messages.raw_json` 保存原始 Webhook 事件,未來重跑分類或除錯都有依據。
3. **安全基線已到位**:簽章驗證(錯誤回 401)、管理 API Bearer 驗證、密鑰不進版控、敏感路徑掃描回 404、文件本身不含密鑰。
4. **可維運性**:故障排查有明確順序(LINE 狀態頁 → Console 設定 → Webhook POST → HTTP 狀態碼分流 401/500),測試程序可重現(唯一測試字串 + 可分類文字 + 附件)。
5. **行事曆輸出規則合理**:只輸出有 `due_at` 且非 done/cancelled 的項目。

## 4. 風險與弱點分析

依優先順序排列:

### P1(建議儘速處理)

| # | 風險 | 說明 | 建議 |
|---|---|---|---|
| 1 | 單一 ADMIN_TOKEN 權限過大 | 同一把 token 同時管儀表板、全部 API 與行事曆;行事曆又以 URL query 傳遞,容易殘留在瀏覽器紀錄、代理日誌或被誤轉貼 | 為行事曆發獨立唯讀 token、可輪替;管理 token 與訂閱 token 分離(文件 §14 已列入建議,應提前) |
| 2 | 無群組白名單 | 任何人把官方帳號拉進任意群組,系統就會開始保存該群組內容,有法律與商譽風險 | 加入 group_id 白名單,非白名單群組自動退出或不寫入 |
| 3 | Webhook 漏接無補救 | LINE 未成功投遞時系統完全不知道有訊息存在;附件還有下載期限,過期即永久遺失(7/28 故障即為實例) | 加入投遞監控/告警;故障恢復後以人工重送測試訊息確認(已為既定程序);評估 redelivery 成效並記錄漏接區間 |

### P2(近期規劃)

| # | 風險 | 說明 | 建議 |
|---|---|---|---|
| 4 | 個資與資料保留 | 系統長期保存成員發言、顯示名稱與檔案,尚無成員告知、保留期限與刪除機制 | 訂定保留政策、群組公告告知、提供刪除流程(文件 §14 已列) |
| 5 | OpenAI 單點依賴 | Key 失效、配額用盡或服務異常時文字不分類;目前僅能事後從「有保存但沒分類」發現 | 分類失敗時標記重試佇列;監控分類成功率;`raw_json` 已可支援事後補跑 |
| 6 | 密鑰有效性無主動監控 | Channel Access Token、OpenAI Key、ADMIN_TOKEN 失效只會以功能靜默失敗呈現 | 定期健康檢查(文件 §14 已列),失敗即通知 |

### P3(觀察即可)

| # | 風險 | 說明 |
|---|---|---|
| 7 | `room` 類型不支援 | 舊式多人聊天室訊息靜默丟棄;若公司實務上不用 room 可維持現狀,但應讓成員知道此限制 |
| 8 | 背景模式無回饋 | 機器人不回話,一般成員無從得知訊息是否被記錄;測試依賴儀表板,屬設計取捨 |

## 7. 結論

系統已達可正式運作狀態,設定文件品質足以支撐交接與維運。下一階段重點不在功能擴充,而在**治理與韌性**:token 分權與輪替、群組白名單、Webhook 監控告警、個資保留政策。7/28 的官方故障同時驗證了故障排查流程有效(能在短時間內定位為外部事故),也暴露了「漏接無補救」是目前最需要補上的韌性缺口。
