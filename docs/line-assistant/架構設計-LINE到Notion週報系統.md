## 0. 設計前提（先確認這三件事，否則後面全錯）

### 0.1 LINE Webhook 只能有一個目的地

一個 LINE Messaging API Channel 只能設定一組 Webhook URL。目前這個位置是：

```
https://line.niddesignlab.com/webhook/line
```

**n8n 不可以直接接 LINE。** 若把 Webhook 改指向 n8n，現有的 D1 訊息保存、R2 附件備份、OpenAI 分類會全部斷掉。

### 0.2 因此採用「雙軌」資料流

| 軌道 | 用途 | 失敗後果 |
|---|---|---|
| **即時軌**：Worker → n8n Webhook（fire-and-forget） | 群組註冊指令、當日同步、即時通知 | 漏一筆不影響週報（週報不依賴它） |
| **批次軌**：n8n → Worker `/api/export`（每週拉取） | 週報唯一資料來源（authoritative） | 這條掛了才會缺週報，可重跑補送 |

**原則：即時軌可以掉，批次軌不能掉。** 所有「一定要正確」的產出都走批次軌，因為 D1 是唯一真實來源（single source of truth）。

### 0.3 群組會無限增生，所以「註冊」必須自助化

你會有 業主群 / 設計群 / 工程群 / 軟裝群 / 空調群 / 水電群 / 廚具群…，而且每個新案子都會再長一輪。
如果每開一個群都要你手動去後台填 Group ID，這套系統三個月內就會失效。

**解法：群組自我註冊協定（見 §2.1）。** 你在群裡 @ 小助理講一句話，它自己歸類、自己寫進 Notion 登錄表。

## 2. 流程（Process）

### 2.1 群組自助註冊協定 ★ 這是整套系統的降阻力關鍵

#### 觸發

你把小助理拉進新群後，在群內發一則訊息，**@ 提及小助理**並描述群組。兩種寫法都吃：

**寫法一（自然語言，推薦）**
```
@川果設計 NID DESIGN LAB 這是文心南六路的空調施工群，主要跟冠翔空調對接進度和圖說
```

**寫法二（結構化，最不會出錯）**
```
@川果設計 NID DESIGN LAB 註冊 專案=文心南六路 類型=空調群 廠商=冠翔空調
```

#### 處理流程

```
群內 @提及訊息
   │
   ▼
Worker webhook 判斷：是否為指令？（訊息含 mention + 註冊關鍵字）
   │  否 → 走原有流程（存 D1、分類），保持靜默
   │
   ▼ 是
Worker 轉發到 n8n /webhook/line-register
   │
   ▼
n8n：LLM 解析 → 比對 Notion「專案」資料庫做模糊配對
   │
   ▼
回覆群組確認卡片（此時小助理「會」說話）：
   ┌─────────────────────────────┐
   │ 已辨識：                     │
   │ 專案：文心南六路 (WXN6)       │
   │ 類型：空調群                 │
   │ 週報排序：第 5 段            │
   │                             │
   │ 正確請回覆「確認」            │
   │ 需修改請回覆「類型=工程群」   │
   └─────────────────────────────┘
   │
   ▼ 收到「確認」
寫入 Notion「群組登錄」資料庫 + 寫回 Worker /api/registry
   │
   ▼
回覆：「✅ 已登錄，本群將納入 文心南六路 週報」，之後恢復靜默
```

#### 靜默規則（重要）

小助理**只在下列情況說話**，其餘一律不回應：

| 指令 | 回應 |
|---|---|
| `@小助理 註冊 …` / `@小助理 這是…群` | 確認卡片 |
| `@小助理 確認` | 登錄成功訊息 |
| `@小助理 狀態` | 本群登錄狀態、本週已記錄則數 |
| `@小助理 停用` | 停止納入週報（訊息仍保存） |
| 其他所有訊息 | **不回應**（維持現有背景記錄模式） |

> 這解決了原分析文件 §4 P3-8「背景模式無回饋」的問題，同時不會讓小助理在業主群裡亂講話。

#### 未註冊群組的處理

- 訊息**照常保存**到 D1（不會遺失）
- 標記 `registry_status = unregistered`
- **不納入任何週報**
- 每週一 09:00 在 Slack 管理頻道 `#系統告警` 列出「待歸類群組清單」，附上群組名稱、訊息則數、最近發言，你點一下就能補登

### 2.2 即時資料流（每則訊息）

```
LINE 群組訊息／圖片／檔案
   │
   ▼
Worker /webhook/line（既有）
   ├─ 驗證 X-Line-Signature
   ├─ 存 D1 messages（含 raw_json）
   ├─ 附件 → 下載 → R2 → D1 attachments
   ├─ OpenAI 分類 → D1 items
   └─ 【新增】非阻塞轉發 → n8n /webhook/line-ingest
                              │
                              ▼
                    n8n：判斷是否為指令
                      ├─ 指令 → 註冊流程（§2.1）
                      └─ 一般訊息 → 不動作（週報時批次處理）
```

**新增的轉發必須是非阻塞的**：`ctx.waitUntil(fetch(...))`，且不檢查回應。n8n 掛掉不能影響 LINE Webhook 回 200，否則 LINE 會判定投遞失敗並重送，造成重複資料。

### 2.3 週報產生流程（每週一）

```
週一 08:30 (Asia/Taipei) n8n Cron 觸發
   │
   ▼
[1] 讀 Notion「專案」資料庫 → 取得所有「進行中」專案
   │
   ▼  （以下對每個專案平行處理）
[2] 讀 Notion「群組登錄」→ 取得該專案的所有 LINE 群組 + 排序權重
   │
   ▼
[3] 抓 Slack 內部討論
     conversations.history(channel, oldest=上週一, latest=上週日)
     → 過濾 bot 訊息、過濾 join/leave
   │
   ▼
[4] 抓 LINE 各群組討論
     GET /api/export?group_id=…&from=…&to=…
     → 回傳該區間 messages + items + attachments
   │
   ▼
[5] 去重
     跨群轉貼的相同內容以 normalized text hash 去重，只保留最早一則
   │
   ▼
[6] 分段摘要（每個來源獨立呼叫 LLM，避免一次塞爆 context）
     - Slack 內部 → 1 次
     - 每個 LINE 群組 → 各 1 次
   │
   ▼
[7] 總體摘要（把 [6] 的所有分段摘要合併，再呼叫 1 次 LLM）
     → 產出 結論 / 代辦 / 追蹤
   │
   ▼
[8] 追蹤項目比對
     讀上週的「待辦事項」資料庫 → 標記：已完成 / 延續中 / 逾期
     → 計算「連續追蹤週數」
   │
   ▼
[9] 寫入 Notion「週報」資料庫（狀態 = 草稿）
     + 寫入「待辦事項」資料庫（新增 / 更新狀態）
   │
   ▼
週一 09:00
[10] 發布到 Slack（Block Kit）
[11] Notion 狀態 → 已發布，回填 Slack permalink
```

### 2.4 附件處理策略

| 情況 | 做法 |
|---|---|
| 一般圖片／檔案 | Notion 週報頁面內只放「本週檔案清單」表格 + R2 簽章連結，**不上傳到 Notion** |
| LLM 判定為重要（圖說確認、簽核文件、驗收照） | 上傳實體檔案到該週報 Notion 頁面 |
| 影片／音訊 | 一律只放連結（Notion 容量與載入速度考量） |

> 理由：一個案子一年會累積數千張現場照，全部塞進 Notion 會讓資料庫變慢且吃爆容量。R2 才是檔案倉庫，Notion 是索引與檢索層。

| 附件數 | Number | | |
| 新增待辦數 | Number | | |
| 本週完成數 | Number | | |
| 逾期待辦數 | Number | | **最重要的健康指標** |
| 議題標籤 | Multi-select | 設計變更／追加預算／工期延誤／材料選樣／驗收缺失／請款／法規／客訴 | **日後檢索的主力**，比全文搜尋準 |
| 涉及金額變動 | Checkbox | | 一鍵撈出所有跟錢有關的週 |
| 決策摘要 | Text | 本週最重要的 1-3 個決策 | 屬性層可預覽，不用點進頁面 |
| Slack 連結 | URL | Slack permalink | 雙向回溯 |
| 生成耗時（秒） | Number | | 系統效能監控 |
| 資料完整度 | Select | 完整／部分缺漏／來源異常 | Webhook 漏接時誠實標記 |

> **關於「還可以有什麼屬性」的建議理由**：
> 1. `ISO 週次` — Notion 的 Date 篩選做「同一週跨專案比對」很痛苦，一個文字鍵值 `2026-W32` 可以直接 Group by，這是投報率最高的欄位。
> 2. `議題標籤` — 半年後你要找「哪幾次談到追加預算」，全文搜尋會撈出一堆雜訊；Multi-select 過濾一秒到位。
> 3. `逾期待辦數` + `風險等級` — 讓你能建一個「紅燈看板」View，只顯示風險≠正常的週報，不用逐週翻。
> 4. `資料完整度` — 對應原分析文件 P1-3「Webhook 漏接無補救」。系統要誠實告訴你「這週資料可能不全」，比假裝完整危險得多。

#### 三段的定義（給 LLM 的判準，避免每週飄移）

| 段落 | 定義 | 不該放什麼 |
|---|---|---|
| **結論** | 本週**已拍板、不會再變**的決定 | 還在討論的事、進度描述 |
| **代辦** | 有**明確負責人**且**未完成**的行動 | 沒有負責人的模糊期待 |
| **追蹤** | **跨週未結案**的事項（來自 DB-4） | 本週新產生且本週已完成的事 |

> 這三個定義必須寫死在 prompt 裡。沒有明確判準，LLM 每週的分類邏輯會漂移，你三週後就會不信任它。
